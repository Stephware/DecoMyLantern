# BeMyParol friend invitation workflow

The current system gives each seasonal parol **one** invitation. New parols issue it automatically. Existing parols issue it on their next owner dashboard visit. The same link is always returned: no link history, additional link creation or revoke controls.

## Owner and database

- The API generates one **16-character URL-safe token** from 12 cryptographically random bytes (96 bits). The public URL uses `https://bemyparol.site/#/i/<token>`.
- `POST /api/my/lantern/invitations` is idempotent: it retrieves or creates that one official link. The owner dashboard automatically calls it and shows **Copy invitation link**.
- The existing SQL Server `ShareLinks` table has a new `IsOfficial` flag and `EncryptedToken` column, enforced by a filtered unique index on `LanternId` when `IsOfficial = 1`.
- The token hash remains SHA-256. The original token is available again only by AES-256-GCM decryption using the server's persistent `Invitations:EncryptionKey` secret.
- Historical links remain in the database with `IsOfficial = 0`. All old URLs are retired, but their contributions, light positions and private messages stay intact.
- The official invitation expires December 31 at 23:59:59 Philippine time of its parol's season. Each new Christmas season has a separate parol and link.

**Before starting or upgrading:** Set `Invitations:EncryptionKey` to a single long-lived Base64-encoded 32-byte random key, e.g. generated by `openssl rand -base64 32`. Store it in ignored local user secrets, or in the Docker `INVITATION_ENCRYPTION_KEY` variable. Keep this key backed up securely, and identical across backend replicas. Changing it makes previously issued links undecipherable.

Apply the new EF migration `20261020220000_SingleInvitationLink` before starting the updated API. The checked-in `database/schema.sql` contains the corresponding idempotent SQL section. Do not edit previously applied migration history.

## Guest

1. A guest opens the one short link. The URL fragment is not sent as an HTTP path/query; React posts the token in JSON.
2. `POST /api/invitations/preview` checks the official link, expiry and token hash, then returns public parol data without private message bodies, owner identity or other contributors' names.
3. The guest supplies a name (1–80 characters) and optional Christmas message (up to 500 characters).
4. `POST /api/invitations/contribute` validates the 43-character guest-browser cookie, CSRF token and invite, then uses a serializable database transaction and unique constraints to assign exactly one light per guest browser.
5. The owner receives the extra light; private messages remain sealed until December 25, Philippine time.

A browser cookie does not prove a guest is a unique human. Keep rate limiting and moderation safeguards before public launch.

## Endpoints

| Method | Route | Behavior |
| --- | --- | --- |
| POST | `/api/my/lantern/invitations` | Retrieve or create the same single official link for its owner |
| GET | `/api/invitations/csrf` | Set guest cookie and issue CSRF token |
| POST | `/api/invitations/preview` | Return safe preview and current contributor slots |
| POST | `/api/invitations/contribute` | Add one accepted light and optional private message |

## Validation

Run `node scripts/invitation-smoke.mjs --confirm-dev-database` only against a disposable local database after applying migrations. It creates real test owners and 51 contributions, verifies stable invitation reuse, duplicate prevention, simultaneous contributions, Christmas inbox redaction and reusable recovery access. Do not run it against production.

Also run frontend lint/typecheck/build/tests and backend tests locally, and verify copy/paste, refreshed dashboard, a private-browser guest contribution, migration of an existing parol, rejection of a retired old link and the December 31 cutoff.
